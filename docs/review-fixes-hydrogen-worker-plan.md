# AGY Hydrogen 워커 수정 지시서

## 역할과 목표

사용자는 AGY(Antigravity)의 Hydrogen을 구현 워커로 사용하고, 상위 Codex는 계획·지시·검토만 담당하도록 요청했다. 당신이 구현, 테스트, 문서와 작업 이력 갱신을 수행한다. 상위 에이전트에게 구현을 떠넘기지 않는다.

현재 작업 디렉터리는 `C:\Users\abcde\Desktop\웹소설\stock-sys`다. 현재 체크아웃에서 작업한다. `docs/code-review-2026-11-16.md`에 기록된 11개 문제를 검증하고 모두 해결한다. 보고서 주장을 그대로 가정하지 말고 현재 코드에서 재확인한다. 부정확한 지적은 근거를 들어 정정하되 실제 사용자 흐름을 완성한다.

## 필수 제약

- AGENTS.md를 읽고 준수한다. Next.js 코드를 작성하기 전에 관련 `node_modules/next/dist/docs/` 문서를 읽는다.
- 기존 사용자 변경을 보존한다. 시작 시 HISTORY.md에는 staged/unstaged 변경이 있고, 리뷰 보고서 및 debug.log 등 추적되지 않은 파일이 존재할 수 있다. reset, clean, 무관한 수정 되돌리기 금지.
- 커밋, 푸시, 배포, 운영 데이터 초기화는 수행하지 않는다. 로컬 수정과 격리된 테스트를 끝낸다.
- 대규모 디자인 변경이나 프레임워크 교체를 하지 않는다. 기능 수정에 필요한 화면 연결만 수행한다.
- 로그인/권한 검사를 삭제하거나 cash 직접 수정 차단을 해제해서 기능을 복구하지 않는다.
- 외부 DB나 유료 서비스를 새로 전제하지 않는다. 현재 독립형 실행 방식에서 내구성 및 공유 한계를 명시적으로 다룬다. 새로운 의존성이 필요하면 최소화하고 근거를 보고한다.
- 실제 사용자 데이터가 있는 `.data`를 테스트로 덮어쓰지 않는다. 저장 테스트는 임시 디렉터리와 격리된 DB 인스턴스를 사용한다.
- 거래 이력의 롤링 캡, 주문·계좌 동시성 보호, 기관 자산 장부, 정산 멱등성을 유지한다.
- 주식/옵션/원자재의 단위와 계약 승수, 수수료, 예약 자산을 서버에서 계산한다. 클라이언트의 잔액·가격·권한 주장을 신뢰하지 않는다.

## 실행 계획

### 1단계 — 입력·권한·정보 공개 경계

1. 원자재 주문의 객체 구조, 종목 존재, side/type enum, 가격·수량의 타입/유한성/양수/정수 조건을 서버에서 검증한다. 시장가와 지정가의 가격 규칙을 구분한다. 잘못된 잔량에 대해 매칭 루프가 반드시 진행하거나 종료되도록 방어한다. 숫자가 아닌 수량을 포함한 입력은 등록 전에 400으로 거절한다.
2. 원자재 이벤트 수동 주입은 기존 관리자 검증을 사용한다. 주문자는 서버 세션에서 결정하며 body의 userId/botId 등 참여자 위조를 거절하거나 안전하게 제거한다. 개발 게스트 정책은 다른 API와 일치시킨다.
3. 프로필 UPDATE를 이름 등 필요한 필드의 명시적 허용 목록으로 바꾼다. 외화 잔액, 라이선스, 해금, 구독, 권한과 자산 필드는 직접 갱신할 수 없게 한다. 잘못된 payload도 처리한다.
4. 개인 주문 조회는 항상 세션 사용자로 제한한다. 공개 호가 조회는 가격별 집계 등 개인정보가 없는 별도 응답 경로를 사용한다. 기존 useOrderbookData 등 사용처를 찾아 호환성을 유지한다. 공개 trades/정산 테이블도 동일한 개인 식별자 노출이 없는지 확인한다.
5. 프로덕션의 비로그인/로그아웃 사용자가 클라이언트에서 guest로 다시 로그인된 것처럼 보이지 않게 한다. 개발용 게스트는 명시적인 개발 환경에서만 제공하며 서버/클라이언트 정책을 통일한다.

검증: 비로그인/일반 사용자/관리자 별 API 권한, 필드 위조, 필터 생략 우회, 정상 공개 호가 렌더링을 확인한다. 위험 입력의 매칭 테스트는 시간 제한이 있는 격리 프로세스로 실행해 테스트 주 프로세스를 멈추지 않게 한다.

### 2단계 — 자산 장부와 내구성

6. 런타임 저장/복원 경로를 연결한다. 저장 실패 후 성공 응답, 복원 전 주문 처리, 중간 거래 상태 저장, 여러 저장 작업의 파일 경합을 방지한다. 단순 30초 자동 저장만으로 '확정 거래 영속성 완료'라고 보고하지 않는다. 시작·종료·확정된 거래와 설정 변경의 내구성 경계를 정의하고 구현한다. 파일 저장을 택하면 원자적 교체와 실패 처리, 단일 writer 보호가 필요하다. 여러 프로세스/인스턴스가 동일 파일을 덮어쓰는 구성을 허용하지 않거나, 일관된 공유 권위를 구현한다.
7. 스냅샷에 정산 멱등 원장, LP 부채 및 관련 상태, 옵션/채권 정산 상태 등 복원에 필요한 모든 권위 데이터를 포함한다. 구버전 스냅샷의 안전한 마이그레이션/거절 정책과 손상 데이터 처리, 인덱스 재구성을 포함한다. 저장 내용에 없는 권위 상태가 초기값으로 조용히 돌아가지 않게 한다. 별도 engine-server와 Next.js 엔진이 각각 독립 시장으로 동작한다면 저장소 소유권도 구분한다.
8. 원자재 주문의 증거금 예약과 사용자 포지션/현금 정산을 서버 권위 장부에 연결한다. 클라이언트 cash UPDATE를 제거한다. 주문 접수, 부분 체결, 미체결 주문 만료/취소, 실패 시 롤백 및 예약 해제를 처리한다. 같은 계좌의 동시 주식/원자재 주문이 잔액을 중복 사용하지 못하게 한다. 현금·증거금·포지션을 실제로 바꾼 결과만 UI에 성공으로 표시한다.
9. 원자재 오더북 내부의 불필요한 무한 체결 이력은 제거하거나 제한한다. settlementLedger는 멱등성이 필요한 원장이므로 단순 cap 삭제 금지. 적절한 내구성 있는 보관/인덱스 또는 안전한 재실행 거절 정책을 사용해 무한 RAM 누적을 해결한다. 일반 거래 표시 데이터의 캡은 그대로 유지한다.

검증: 새 인스턴스 및 별도 프로세스에서 저장 후 재시작 복원, 동일 거래 재전송, LP 부채 및 파생 정산 복원, 저장 실패, 증거금 부족, 동시 주문, 부분 체결·만료·취소를 검증한다. 어떤 내구성 보장을 구현했는지 정확히 보고한다.

### 3단계 — 실제 사용자 기능 완성

10. 옵션 HTS에 실제 선택 계약 ID와 계좌 잔액을 연결하고 서버 주문 경로로 제출한다. 기본 1천만 원 가짜 잔액과 무조건 성공 alert를 제거한다. 응답 실패는 실패로 표시한다. 화면의 지정가/시장가/조건부/최유리/IOC/FOK 중 실제 지원하지 않는 방식은 지원한다고 표시하지 않거나 정확하게 구현한다. 옵션 계약 승수와 만기, 매수·매도 가능 여부를 서버에서 검증한다.
11. 상점 전용 서버 구매 처리로 서버의 상품 가격 확인, 계좌 잠금, 현금 차감, 라이선스/구독 부여를 원자적으로 수행한다. 클라이언트의 가격/차감 잔액/권한 payload는 신뢰하지 않는다. 미구현 media_outlets 카탈로그를 현재 서비스에 맞게 제공한다. 뉴스 구독과 모든 현재 상품의 구매/중복 구매/잔액 부족 처리를 확인한다. 30일 상품은 실제 만료를 처리하고 권한 소비처에도 반영한다.
12. 환전 RPC 또는 전용 API를 구현한다. 세션 사용자, 허용 통화, 유효 금액, 서버 환율, 소수점/반올림과 수수료 정책을 확인하고 두 잔액을 원자적으로 갱신한다. 요청의 다른 사용자 ID는 신뢰하지 않는다. 존재하지 않는 RPC는 명시적 오류로 반환한다. 기본 및 v2 화면 모두 확인한다.

검증: 옵션 주문은 실제 서버 주문/체결/계좌 변화로 확인한다. 상점은 구매 전후 현금과 권한, 환전은 양 통화 잔액과 실패 시 무변경을 확인한다. 기존 화면과 v2 화면에서 정상이던 경로를 유지한다.

### 4단계 — 전체 회귀·보고

- 각 변경에 맞는 동작 검증을 작성/실행한다. 구현 구조를 그대로 복제하는 형식적 테스트가 아니라 기존 결함을 재현하고 수정 후 통과하는 테스트를 사용한다.
- 루트와 engine-server 타입 검사, 프로덕션 빌드, ESLint, Phase 1 9개 테스트를 실행한다.
- 정산/거래 격리/주문 보안/파생상품 관련 기존 Phase 2–4 회귀 중 실제 영향받은 경로를 선택해 실행한다. 실패가 있으면 원인을 해결하고 재검증한다. 무관한 기존 실패라면 재현 근거와 범위를 구분해서 보고한다.
- 가능하면 실제 HTTP 요청 및 브라우저에서 로그인 상태별 핵심 흐름을 확인한다. Orca 브라우저를 사용한다면 해당 스킬 지침을 따른다. 외부 OAuth가 없어 검증할 수 없는 부분을 테스트 통과로 과장하지 않는다.
- `docs/code-review-2026-11-16.md`의 11개 지적마다 수정 파일, 처리 결과, 검증 증거, 남은 제한을 적은 대응 문서를 `docs/review-fixes-verification.md`로 작성한다.
- HISTORY.md 맨 아래에 실제 구현과 테스트 결과를 한국어로 append한다. 기존 staged/unstaged 기록을 보존한다.

## 보고·질문 규칙

- 주요 단계 완료 시 상위 코디네이터에게 변경 요약과 검증 결과를 보낸다. 단계 보고만으로 전체 작업을 완료 처리하지 않는다.
- 위 범위 내 통상 구현 선택은 자율적으로 진행한다. 다만 기존 제품 동작을 바꾸는 필수 결정이나 안전하게 해결할 수 없는 장애는 Orca orchestration ask로 코디네이터에게 질문한다.
- 완료 보고에는 11개 항목별 완료 여부, 수정 파일, 실행한 명령과 실제 종료 결과, 데이터 내구성 보장, 미해결 제약을 포함한다. 실행하지 않은 검증은 실행했다고 적지 않는다.
- 모든 필수 작업과 검증이 끝난 뒤에만 worker_done으로 성공을 보고한다. 하나라도 필수 항목이 미완료면 그 상태를 명시한다.
