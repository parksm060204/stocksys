# 코디네이터 후속 수정 지시 — 중단 지점 재개

사용자가 중단 지점부터 이어서 작업하도록 요청했다. 이전 수정과 추가 루프 완료 보고는 확인했으나, 코디네이터가 현재 코드에서 아래 필수 보완을 발견했다. 원래 지시서 `docs/review-fixes-hydrogen-worker-plan.md`와 기존 변경을 유지하며 **AGY Hydrogen 워커가 구현·검증**한다. 코디네이터는 직접 애플리케이션 코드를 수정하지 않는다. 이미 완료된 작업을 초기화하거나 처음부터 다시 하지 않는다.

## A. 옵션 지정가가 임의 체결·현금 생성 경로가 됨

`app/api/options/order/route.ts`는 LIMIT의 body.price를 그대로 execPrice로 사용하고 상대 주문·LP/발행자 장부 없이 보유량과 현금을 바꾼다. 작은 가격으로 매수 후 임의의 큰 가격으로 매도하면 현금이 생긴다. 실제 지정가 의미(매수 상한/매도 하한)를 구현하고 서버 권위 유동성·가격·상대방/발행자 정산을 통해 체결한다. 비시장성 지정가는 미체결로 유지하거나 명시적으로 거절하며 성공 체결로 표시하지 않는다. 기존 옵션 정산/원장에 연결하고 실제 fee, 승수, 계약 만기, 서버의 라이선스/기간 권한 검사도 확인한다. 입력은 유한해도 곱셈 후 Infinity/안전 정수 초과가 생길 수 있으므로 계산 결과 범위도 검증한다.

필수 재현: 임의의 낮은 매수가/높은 매도가로 무위험 현금 생성 불가, 비시장성 지정가 미체결, 실제 상대방 자산 보존, 저장 실패 무변경, 만료/무권한 거절. 단순 UI 제한으로 해결하지 않는다.

## B. 주식 정산 원장 트리밍 후 멱등성이 실제 호출 경로에서 깨짐

`InMemorySettlementRepository.isTradeSettled(tradeId)`는 `db.isTradeAlreadySettled(tradeId)`만 호출한다. 새 createdAtIso 인자를 전달하지 않으므로 trimSettlementLedger에서 ID 삭제 후 실제 배치 경로가 워터마크 검사를 사용하지 않는다. 헬퍼에 timestamp를 직접 넣는 테스트만으로 통과 처리하지 않는다. 또한 요청자가 created_at을 바꾸거나 ID를 재사용하는 경우를 고려해야 한다. 권위 원장/일련번호/안전한 재실행 거절 정책을 설계하여 메모리 제한과 멱등성을 동시에 만족시킨다. 정상 신규 거래를 임의로 기존 거래로 판단해 건너뛰어서도 안 된다.

필수 재현: 실제 repository/batch 경로로 거래 정산 → 원장 트리밍 → 동일 ID 재전송(타임스탬프 누락·변경 포함) → 현금·보유량·거래·원장 무변경. 재시작 복원 이후에도 동일하게 검증한다.

## C. 원자재 원장의 단순 cap 삭제와 재시작 ID 충돌

`commodityLedger.ts`에서 commoditySettlementLedger를 5,000건으로 단순 삭제해 오래된 체결 재전송을 다시 처리할 수 있다. 사용자 지시서에 명시한 멱등 원장 단순 cap 삭제 금지를 준수한다. `CommodityMarketEngine`의 currentTick/userOrderSeq 및 `trade_<commodity>_<tick>_<seq>` 식별자가 재시작 시 초기화되는 반면 원장은 복원되므로 새 거래를 이전 거래로 오인할 수도 있다. 주문·체결의 권위 ID/세션/시퀀스와 재생 방지를 영속적으로 관리한다.

필수 재현: 5,000건 초과 정산 후 오래된 거래 재전송 차단, 스냅샷 복원 후 신규 체결을 정상 정산, 재시작 전 ID 재사용 방지.

## D. 원자재 체결을 정확한 주문 예약에 귀속하고 원자적 정산

현재 CommodityTrade에는 buy/sell order ID가 없고 `settleCommodityTradeForUsers`는 같은 사용자/종목/방향의 첫 예약을 찾아 전체 trade.size 포지션을 만든다. 실제 체결된 주문이 더 늦게 낸 주문이면 잘못된 예약을 소진하고 일부 수량이 무증거금 포지션이 될 수 있다. 체결에 양쪽 주문 ID를 포함하고 정확한 잔량/예약을 검증하며 실패 시 양쪽 장부와 오더북을 원자적으로 롤백한다. 자기매매도 처리한다.

`nextTick()`의 void settleCommodityTradeForUsers와 void releaseCommodityOrderMargin은 기다리지 않아 오더북 체결 확정, 계좌 반영, 저장 사이에 경합이 생긴다. 실제 런타임은 비동기 정산·만료 환불을 기다리고 확정 후 저장해야 한다. 호환성이 필요하면 동기 테스트 인터페이스와 권위 런타임 경로를 명확히 나눈다. 증거금/손실 처리를 Math.max(0, cash+delta)로 덮어 손실을 소멸시키지 않는다.

필수 재현: 같은 방향 주문 2개 중 두 번째가 먼저 체결, 서로 다른 수량의 예약, 동시 주식/환전/원자재 체결, 정산 실패 rollback, 자기매매, 포지션 청산 및 손실 보존.

## E. 원자재 미체결 예약이 재시작 후 고립됨

현재 스냅샷은 commodityMarginReservations를 복원하지만 엔진 오더북/currentTick 등은 복원하지 않는다. 사라진 주문의 증거금이 계속 묶일 수 있다. 복원 후 미체결 주문을 일관되게 재구성하거나 재개 전에 안전하게 취소·환불하는 명시적 정책을 구현한다. 엔진은 모듈 import 시 타이머를 바로 시작하지 않고 DB 복원·조정 완료 후 시작한다.

필수 재현: 미체결/부분체결 주문 저장 → 새 프로세스 복원 → 잔량 및 예약 유지 또는 정확한 환불, 중복 환불 없음.

## F. 저장 실패와 동시성 경계가 장부 트랜잭션과 분리됨

`app/api/orders/route.ts` 및 local-db 주문/취소 경로는 LocalMarketService가 체결·취소를 확정하고 락을 해제한 후 저장한다. 실패하면 500만 반환하고 실제 현금·주문·보유량은 남는다. 환전도 계좌 락을 풀고 저장 실패 시 오래된 전체 profile로 복원해 다른 동시 거래를 덮어쓸 수 있다. PersistenceManager는 저장 호출만 직렬화하고 변경 중 스냅샷이나 실패 rollback과 다른 저장의 경합을 막지 않는다.

확정 mutation·durable commit·실패 rollback을 같은 안전한 경계에 넣는다. 전체 DB snapshot rollback으로 다른 계좌의 성공 거래를 지우지 않는다. 봇 엔진과 원자재 자동 체결도 30초 autosave만으로 '확정 거래 내구성'을 주장하지 말고 동일한 commit 경계를 적용한다. engine-server도 현재 30초 autosave만 연결되어 있으므로 확정 거래의 충돌/실패 정책을 점검한다. 파일 single writer가 process 단위뿐이면 두 프로세스가 동일 STOCKSYS_DATA_DIR를 열지 못하도록 실제 소유권 보호를 구현한다. 문서만으로 안전하다고 간주하지 않는다.

필수 재현: 주식 체결/취소/환전의 저장 실패 전후 무변경, 실패 중 다른 계좌 거래 성공 상태 보존, 동시 저장·부분 mutation 스냅샷 배제, 자동 체결 직후 새 프로세스 복원, 동일 저장 경로 두 writer 거절. 테스트는 임시 디렉터리·별도 프로세스에서 실행한다.

## 실행·완료 조건

- A–F를 현재 코드에서 재확인하고 수정한다. 순서는 A/B/C 보안·멱등성 우선, D/E/F 장부/내구성 통합 순서로 잡되 공통 transaction 설계가 필요하면 먼저 설계한다.
- 일상적인 구현 선택은 자율 진행한다. 중요한 아키텍처 결정이 막히면 Orca ask로 코디네이터에게 질문한다.
- 기존 사용자 변경 및 AGENTS.md의 Next 자동 생성 변경을 임의로 되돌리지 않는다. 커밋/푸시/배포/사용자 데이터 초기화 금지.
- 지적을 고칠 때 테스트를 약화하거나 기대값을 새 결함에 맞추지 않는다. 실제 repository/API/재시작 경로로 위 실패를 재현한 회귀 테스트를 남긴다.
- `docs/review-fixes-verification.md`의 기존 '완료/제한 없음' 주장을 실제 보장에 맞게 갱신하고 A–F별 수정·재현 테스트·실제 결과를 기록한다. HISTORY.md에는 실제 작업을 append한다.
- 루트/engine-server 타입 검사, build, ESLint, 기존 영향받은 정산·파생·동시성·멱등성 회귀를 재검증한다. 실패 또는 미구현이 있으면 완료로 보고하지 않는다.
- 모든 후속 수정을 마친 뒤 사용자 요청대로 새 관점의 리뷰 → 발견 문제 수정 → 영향받은 검증을 한 번 수행하고 결과를 기록한다.
- 완료 보고에는 항목별 구현/증거, 실행 명령과 종료 결과, 잔여 제약을 제시한다. 상위 코디네이터가 결과를 검토한다.
