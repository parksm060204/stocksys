## 리뷰 증거와 보고

- 개별 결함마다 독립 번호, 심각도(P0는 조건 없이 서비스 전반을 막거나 즉시 광범위 손실이 확실할 때만), 실제 파일/좁은 행, 호출 경로/발생 조건, 영향, 관측/기대 및 최소 수정 방향을 적는다. 취향/의심을 확정 결함으로 섞지 않는다.
- 금전·내구성·동시성 문제는 격리 실행 반례로 확인한다. 직접 만든 비정상 fixture에서만 발생하는 경우, 외부/봇 실제 활성 경로 도달성 및 outer transaction 보호를 확인해 한계를 명시한다. 재현 코드와 정확한 실행법을 보고서에 남겨 후속 수정 워커가 다시 검증할 수 있게 한다.
- 문제 건수를 채우려 하지 않는다. 기존 해결 항목을 같은 결함으로 중복 세지 않는다. 실제 읽은 범위와 미검토 부분을 표로 밝힌다.
- root/engine tsc, lint, 관련 회귀 테스트 및 기존 실패 테스트를 격리 실행한다. 장기 스크립트는 충분한 stdout buffer(예:50MB)·실행시간과 정상 종료 cleanup을 고려한다. 실패를 수정하지 말고 exit/실제 오류를 기록한다. 이번 리뷰에서 실패를 발견하는 것은 과제 실패가 아니다.
- 가능하면 사용자가 겪는 실제 브라우저/HTTP 흐름도 확인한다. 브라우저를 쓸 때 orca-cli 스킬을 읽는다. 실행하지 않은 build/브라우저/OAuth/원격 DB는 검증됐다고 쓰지 않는다.
- HISTORY.md에 실제 리뷰 결과를 추가한다. 결과 문서에 후속 수정을 위한 우선순위와 항목별 검증 조건을 포함한다. 로컬 링크는 /C:/.../file.ts:행 형식을 쓴다.
- 반드시 worker_done으로 결과 보고를 한다. 검증을 시작했다는 말만 하고 턴을 끝내지 말고 실행 결과를 회수한다. 보고서 경로, 확정/검증불가 구분, 주요 문제와 실행 검사 결과를 보고한다. 수정은 코디네이터의 후속 지시를 받은 다음 진행한다.
