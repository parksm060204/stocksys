검토는 전체 구조와 주요 실행 경로를 중심으로 했다. 모든 소스 파일의 모든 줄을 감사했다는 의미는 아니다.

## P1 — 우선 수정 필요

### 1. 일반 주식 주문 경로로 옵션 승수·자격·만기 검사를 우회할 수 있음

- 위치: `app/api/orders/route.ts:51`, `app/api/local-db/route.ts`의 `submit_and_match_order`, `lib/engine/dbMatching.ts:79`.
- 조건: 주식 주문의 `stock_id`에 실제 옵션 계약 ID를 넣는다. API는 문자열 여부만 검사하고, 공통 매칭 서비스도 주식 종목 등록 여부를 검사하지 않는다. 주식과 옵션 주문은 같은 `db.orders`를 사용한다.
- 결과: 옵션의 대기 매도 주문이 주식 정산의 `price × size`로 체결된다. 옵션 승수, 거래 자격증, 만기 검사를 거치지 않는다. 반대로 일반 주문 경로에서 만든 옵션 ID의 매수 주문이 옵션 서비스의 매칭 후보가 될 수도 있다.
- **직접 재현:** 승수 250,000, 가격 10인 옵션 1계약을 매도 대기시킨 뒤, 자격증 없는 매수자가 주식 서비스로 제출했다. `success=true`, 보유 옵션 1계약이 생겼고 매수 현금은 1,000원에서 **989.975원**으로 감소했다. 정상 계약 대금은 수수료 전 **2,500,000원**이다. HTTP 요청 자체가 아닌, API가 호출하는 동일 매칭 함수에 직접 입력해 확인했다.
- 수정 방향: 일반 주문 경계에서 허용된 자산 종류와 종목 존재 여부를 검증한다. 자산 유형에 따라 권위 정산 서비스를 분기하고, 같은 주문 저장소를 쓸 때에도 자산 종류가 다른 경로에서 처리되지 않게 한다.

### 2. 실패한 거래의 중간 상태가 다른 거래의 성공 스냅샷에 저장됨

- 위치: `lib/memoryDb/PersistenceManager.ts:26`, `:66`, `:74`; 각 서비스의 상태 변경 후 `onPersist()` 호출.
- 조건: 서로 다른 계좌 A/B가 동시에 변경된다. A의 디스크 저장을 대기시키고, 그동안 B가 전체 DB 스냅샷을 추출한다. A 저장은 실패하고 B 저장은 성공한다.
- 원인: `withCommitGate`는 스냅샷 추출만 감싼다. 실제 상태 변경과 실패 시 롤백은 이 게이트에 참여하지 않는다. 저장 큐의 직렬화만으로 미확정 상태의 직렬화를 막을 수 없다.
- **직접 재현:** 메모리 전용 저장 어댑터에서 A 환전 저장을 실패시키고 B 환전 저장을 성공시켰다. 결과는 `A=false`, `B=true`였지만 A 현금은 **메모리 1,000원 / 마지막 성공 스냅샷 862원**이었다. 재시작하면 실패했다고 응답한 환전이 적용된다.
- 수정 방향: 변경 시작부터 저장 성공/실패 및 롤백까지 하나의 커밋 경계로 묶거나, 미확정 변경이 전역 DB에 보이지 않는 트랜잭션 상태에서 커밋 스냅샷을 구성한다. 자동 저장도 같은 경계를 따라야 한다.

### 3. 원자재 틱 롤백이 이미 성공한 다른 거래를 덮어씀

- 위치: `lib/commodities/CommodityMarketEngine.ts:425`, `:472`, `:483`, `:495`.
- 조건: 원자재 틱 정산 후 저장이 대기 중일 때 같은 사용자가 환전·상점 구매·다른 주문을 실행한다. 이후 원자재 틱 저장이 실패한다.
- 원인: 개별 체결 정산의 계좌 잠금은 저장 전에 해제된다. 틱 바깥에서 잡은 프로필 복사본으로 전체 필드를 복원하고, `commodityOpenOrders` 전체 Map도 이전 복사본으로 교체한다. 그동안의 정상 변경을 보호하지 못한다.
- **직접 재현:** 원자재 저장 대기 중 같은 계좌의 1,380원 환전이 성공했다. 현금이 **93,250,000 → 93,248,620원**으로 변경된 뒤, 원자재 저장 실패 롤백으로 **93,250,000원**이 됐다. 성공한 환전 결과가 사라졌다.
- 수정 방향: 틱의 계좌 잠금을 커밋/롤백까지 유지하고, 동시 주문 등록도 같은 실행 경계에 참여시킨다. 전체 컬렉션 교체 대신 틱이 소유한 변경만 복구해야 한다. 실패 시 이미 변경한 봇 자산·가격·체결 이력·틱 상태의 복원도 함께 점검해야 한다.

### 4. 환전 반올림으로 반복 수익을 만들 수 있음

- 위치: `lib/exchange/exchangeService.ts:19`, `:89`, `:99`.
- 원인: 송금 통화와 수취 통화를 각각 가장 가까운 최소 단위로 반올림하고, 반올림으로 늘어난 수취 금액의 실제 비용을 청구하지 않는다.
- **직접 재현:** 환율 1 USD = 1,380원에서 **7원 → 0.01 USD → 14원** 환전이 모두 성공했다. 현금 100원이 왕복 한 번으로 **107원**이 됐다. 현재 기본 환율에서도 가능한 경로다.
- 영향: 금액이 작은 요청을 반복해 서버 장부에 없는 가치를 생성할 수 있다.
- 수정 방향: 최소 환전 단위·수취 절사 또는 실제 수취 단위 기준 청구 정책을 명시하고, 최소 단위의 왕복 환전에서 잔액이 증가하지 않는 불변식을 검사한다.

### 5. 자산별 예약금 계산이 달라 같은 현금을 중복 사용함

- 위치: `lib/engine/orderRisk.ts:22`, `lib/options/optionOrderService.ts:222`, `lib/exchange/exchangeService.ts:123`, `lib/commodities/commodityLedger.ts:82`, `app/api/shop/purchase/route.ts`의 현금 검사.
- 원인: 주식 예약 계산은 옵션 승수를 적용하지 않는다. 옵션 서비스는 현재 주문하는 계약과 다른 옵션 계약에 승수 1을 적용한다. 환전·상점·원자재 증거금 예약은 대기 중인 주식/옵션 매수 예약을 차감하지 않는다. 기존 옵션 예약 수수료 처리도 일관되지 않다.
- **직접 재현:** 현금 600,000원에 가격 2, 승수 250,000인 옵션 1계약을 매수 대기 상태로 두었다. 주식 예약 계산은 **500,000원 대신 2원**을 반환했다. 이후 **552,000원 환전도 성공**해 현금 48,000원이 남았다.
- 영향: 나중의 대기 주문 체결 실패, 다른 주문 자금의 소비, 옵션 상대방 현금 음수 등의 위험이 있다.
- 수정 방향: 계약별 승수·수수료를 반영하는 공용 가용 현금 계산기를 만들고, 현금을 사용하는 모든 기능이 계좌 잠금 안에서 이를 사용한다. 이미 현금에서 차감한 원자재 증거금은 이중 차감하지 않아야 한다.

### 6. 별도 engine-server 재시작 시 주문/체결 ID가 이전 실행과 충돌할 수 있음

- 위치: `engine-server/src/index.ts:19`, `:22`; `lib/engine/simulation/runtime/simulationContext.ts:76`; `engine-server/src/MarketEngine.ts:183`, `:254`, `:1319`.
- 원인: DB 스냅샷을 복원하지만 엔진 실행 문맥은 기본값으로 새로 만든다. 기본 runId는 `run_seed_42`이고 틱과 부분체결 시퀀스는 다시 0에서 시작한다. 결정론적 ID 구성에는 이 값들이 들어간다.
- 영향: 복원된 주문/멱등 원장의 ID와 새 ID가 겹쳐 새 주문이 거절되거나 새 체결이 이미 정산된 것으로 처리될 수 있다.
- 검증: 초기화·ID 구성 코드를 확인했다. 실제 엔진 프로세스의 강제 종료/복원 E2E는 실행하지 않았다.
- 수정 방향: PRNG·시계·틱·시퀀스 등 재개에 필요한 상태를 일관되게 복원하거나, 실서비스의 새 실행에는 영속 에포크를 부여한다. 결정론적 테스트의 동일 시드 재현 요구와 운영 재시작 정책을 구분한다.

### 7. 정산 원장 트리밍 후에도 거래 ID가 메모리와 스냅샷에 계속 누적됨

- 위치: `lib/memoryDb/memoryStore.ts:981`, `:1001`, `:1083`; 옵션의 `generateId('opt_tr')`, 별도 엔진의 결정론적 체결 ID 생성 경로.
- 원인: `tr_e<epoch>_<seq>` 형식만 워터마크로 압축한다. 그 외 ID는 `evictedCustomTradeIds`에 영구 추가하고 이 Set 자체도 스냅샷에 포함한다. 현재 옵션·별도 엔진의 체결 ID는 압축 형식에 해당하지 않는다.
- **직접 재현:** 비압축 형식 15건을 원장에 넣고 상한 10건으로 트리밍하면 원장 10건 외에 **Set 5건**, 워터마크 0건이 남는다. 반복 실행 시 Set 상한이 없다.
- 영향: 원장 Map의 상한과 별개로 장기 운영 시 메모리·JSON 크기와 저장 시간이 증가한다.
- 수정 방향: 실제 ID 생성 경로와 압축 정책을 맞추거나, 재실행 방지를 유지하는 디스크 인덱스/아카이브를 사용한다. Set 항목을 단순 삭제하면 멱등성 보호가 사라지므로 주의해야 한다.

## P2 — 기능과 운영 보완 필요

### 8. 자동 체결의 확정 시점과 영속 저장 시점이 다름

- 위치: `lib/engine/localStandaloneServer.ts:156`의 `runTick`, `engine-server/src/index.ts:32`.
- Next.js 내부 엔진은 20틱마다 저장하고 저장 결과 boolean을 검사하지 않는다. 별도 엔진은 기본 30초 자동 저장에 의존한다. 중간에 확정·표시한 자동 체결이 프로세스 비정상 종료 시 사라질 수 있다.
- 수정 방향: 필요한 내구성 수준에 맞춰 틱 커밋 저장 또는 WAL을 연결하고, 저장 실패를 호출자와 상태에 반영한다. 이 문제는 2번의 미확정 상태 혼입 해결과 함께 다뤄야 한다.

### 9. 옵션 시장가 주문이 더 싼 LP 호가보다 비싼 사용자 주문을 먼저 체결함

- 위치: `lib/options/optionOrderService.ts:162`, `:172`, `:182`.
- 사용자 대기 주문끼리만 가격순 정렬해 전량 매칭한 뒤 남은 수량에 LP 호가를 적용한다.
- **직접 재현:** LP 매도 호가 10, 사용자 매도 대기 20인 상태에서 시장가 매수 1계약을 제출하자 **20에 체결**됐다. 동일 시점에 더 낮은 LP 매도 호가가 있어도 선택하지 않는다.
- 수정 방향: LP 호가와 사용자 주문을 하나의 가격 우선 후보 집합으로 비교한다.

### 10. 원자재 증거금·손익 계산이 실제 환율 필드를 읽지 않음

- 위치: `lib/commodities/commodityLedger.ts:15`, `lib/memoryDb/memoryStore.ts:743`.
- 원자재 계산기는 `rate` 또는 `krw_rate`를 읽지만 DB의 필드명은 `rate_to_krw`다. 따라서 정상 USD 행이 있어도 fallback 1,350원을 사용한다.
- **직접 재현:** 기본 DB의 USD 환율 **1,380원**, 원자재 계산기 반환값 **1,350원**을 확인했다. 증거금뿐 아니라 실현 손익 환산에도 적용된다.
- 수정 방향: 환율 레코드 타입과 공용 조회 함수를 통일하고 잘못된 필드명 접근을 타입 검사에서 잡는다.

### 11. 원자재 포지션 청산에도 새 진입과 동일한 추가 증거금을 요구함

- 위치: `lib/commodities/commodityLedger.ts:79`.
- 기존 포지션을 줄이는 주문인지 확인하지 않고 모든 주문에 전체 신규 증거금을 요구한다. 보유 현금을 증거금에 사용한 사용자는 포지션을 닫을 수 없다.
- **직접 재현:** 원유 매수 1계약과 기존 증거금이 있고 가용 현금은 0원인 계좌에서 매도 1계약을 제출하면 **추가 6,750,000원 부족**으로 거절된다.
- 수정 방향: 기존 포지션·이미 제출된 청산 주문을 고려해 위험을 줄이는 수량과 새로 여는 수량을 구분하고 추가 필요 증거금을 계산한다.

### 12. 옵션 계좌 패널의 전체 취소·전체 청산이 실제 거래를 처리하지 않음

- 위치: `app/components/OptionAccountPanel.tsx:10`, `:21`, `:28`.
- `ORD-101` 등의 샘플 주문과 고정 포지션을 표시한다. 전체 취소는 로컬 배열만 지우고 전체 청산은 alert만 띄운다. 실제 API 주문이 생겨도 이 패널은 반영하지 않는다.
- 수정 방향: 본인 주문/보유량을 조회하고 실제 취소·청산 결과를 표시한다. 구현 전에는 실행 가능한 계좌 동작처럼 표시하지 않아야 한다.

### 13. 옵션 체인의 월물 변경이 실제 계약·시세 변경으로 연결되지 않음

- 위치: `app/components/OptionMonthChainGrid.tsx:31`, `:38`, `:77`, `:125`; `app/components/OptionHTSDashboard.tsx:15`.
- 월물 선택은 상태만 바꾸고 행 데이터는 고정 `202608` 티커 배열이다. 실제 DB의 계약 목록은 대시보드에서 조회하지만 이 그리드의 데이터 소스로 전달하지 않는다. 현재 날짜에는 기본 8월물도 이미 지났다.
- 영향: 다른 월물을 선택해도 같은 과거 계약이 선택되고 주문이 만기/계약 불일치로 거절될 수 있다.
- 수정 방향: 현재 유효한 DB 계약을 월물·행사가로 묶어 그리드에 전달하고, 선택 계약 ID와 화면의 티커/가격을 함께 갱신한다.

### 14. ETF 거래가 서버에서 거절돼도 화면에는 체결 완료로 표시됨

- 위치: `app/etf/page.tsx:158`, `:175`, `:198`, `:207`, `:218`, `:244`.
- 현금과 보유량을 먼저 로컬 state에서 변경한 뒤 `profiles`와 `holdings`를 직접 수정한다. `/api/local-db`는 이 자산 변경을 403으로 거절한다. 반환된 `error`를 검사하지 않고 체결 완료 알림을 표시한다.
- 검증: 클라이언트 호출과 서버 접근 제어를 대조했다. 실제 브라우저 클릭은 실행하지 않았다.
- 수정 방향: 서버 주문 API로 거래하고 성공 응답 이후 서버 장부를 다시 조회한다.

### 15. 랜덤 이벤트 선택이 비용·효과·해결 상태를 저장하지 못함

- 위치: `app/components/RandomEventModal.tsx:101`, `:105`, `:107`.
- 현금/패시브와 `active_player_events.status`를 클라이언트에서 수정하지만 각각 서버 허용 정책에 막힌다. 에러 확인 없이 모달만 닫으므로 비용·효과가 반영되지 않고 이벤트가 다시 나타날 수 있다.
- 수정 방향: 세션 소유권, 선택지, 서버 가격을 검증하는 단일 이벤트 처리 API에서 비용 차감·효과 부여·해결 처리를 원자적으로 실행한다.

### 16. 인증 콜백과 일부 읽기 경로가 DB 복원을 기다리지 않음

- 위치: `app/api/auth/[...nextauth]/route.ts:24`, `:55`; `lib/db/server.ts:5`; `app/api/market-flow/route.ts:47`; `app/api/admin/scenarios/route.ts`.
- 인증 콜백은 복원 전 프로필을 생성할 수 있고 자체 저장 경계가 없다. 서버 DB 헬퍼는 비동기 초기화를 시작만 하고 클라이언트를 반환한다. market-flow는 초기화 중 503이 나올 수 있고 관리자 시나리오 경로에는 복원 대기가 없다.
- 영향: 콜드 스타트의 첫 요청 순서에 따라 시드 데이터 노출, 복원에 의한 변경 덮어쓰기, 준비되지 않은 엔진 접근이 발생할 수 있다.
- 검증: 코드 경로 확인. 외부 Google OAuth 로그인과 실제 서버 콜드 스타트 요청 순서 실험은 수행하지 않았다.
- 수정 방향: 서버 데이터 접근의 준비 상태 경계를 통일한다. 인증 콜백에서 초기화를 기다릴 경우 세션 조회와 초기화 사이 순환 호출/교착이 생기지 않도록 인증에 필요한 DB 준비와 엔진 기동을 분리한다.

## 실행한 검증

다음 검사는 모두 종료 코드 0으로 통과했다.

1. `node node_modules/typescript/bin/tsc --noEmit --incremental false`
2. `node node_modules/typescript/bin/tsc -p engine-server/tsconfig.json --noEmit --incremental false`
3. `node --import tsx scripts/test-review-fixes-verification.ts`
4. `node --import tsx scripts/test-followup-a-to-f.ts`
5. `node --import tsx scripts/test-phase1-suite.ts` — 기존 테스트 파일 9개.

추가로 일회성 stdin 스크립트를 별도 Node 프로세스에서 실행해 1~5, 7, 9~11번을 확인했다. 재현은 새 메모리 DB 또는 프로세스 내부 singleton을 사용했으며 실제 스냅샷을 불러오거나 운영 서버에 요청하지 않았다. 2번은 저장 성공/실패 순서를 제어하는 메모리 어댑터, 3번은 원자재 저장 대기를 제어하는 콜백을 사용했다. 회귀 테스트의 실패 주입에 따른 예상 에러 로그는 테스트 실패를 뜻하지 않는다.

일부 tsx 실행은 최초 샌드박스에서 `uv_os_get_passwd ENOMEM`으로 시작되지 않아 승인된 샌드박스 외부 실행으로 재시도했다.

## 미검증 범위

- 프로덕션 빌드 및 실제 브라우저 E2E.
- 실제 Google OAuth 자격 증명을 사용한 로그인.
- 실제 디스크 장애·정전·다중 호스트 파일 잠금·운영 트래픽 부하.
- 별도 engine-server의 실제 프로세스 강제 종료와 재시작 실험.
- 아카이브된 PostgreSQL 구현의 운영 적합성. 현재 주 실행 경로는 메모리 DB이므로 과거 VM DB 체크리스트 충족 여부로 현재 동작을 판단하지 않았다.

권장 수정 순서는 1번 주문 자산 경계, 2~3번 커밋·롤백 경계, 4~5번 금액·예약 불변식, 6~8번 재시작·장기 운영, 이후 자산별 기능과 화면 연결이다.
